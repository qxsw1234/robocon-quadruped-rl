## 一、项目统一设定

* 操作系统：Ubuntu 24.04
* ROS 2：Jazzy
* 仿真器：Gazebo Harmonic，即现代 Gazebo
* ROS 与 Gazebo 通信：`ros_gz`
* 导航框架：Navigation2
* 基础 SLAM：SLAM Toolbox
* 对比 SLAM：Cartographer
* 工作空间：`~/ros2_ws`
* 机器人名称：`diy_nav_bot`
* 世界名称：

  * `simple_world`
  * `complex_world`

计划创建以下 ROS 2 软件包：

```text
ros2_ws/src/
├── diy_nav_description/
├── diy_nav_gazebo/
├── diy_nav_navigation/
└── diy_nav_slam_compare/
```

各软件包职责：

```text
diy_nav_description
├── URDF/Xacro
├── 机器人外观、碰撞体和惯性参数

diy_nav_gazebo
```

# 第0段：给 Codex 的全局工作规则

## 提示词0：全局约束

你现在是这个 ROS 2 项目的开发工程师，同时也是我的教学助手。

我们要完成一个考核项目：

1. 使用 ROS 2 和 Gazebo 搭建自主移动机器人仿真；
2. 自行编写机器人的 URDF/Xacro；
3. 自行搭建 Gazebo 环境；
4. 部署 Navigation2；
5. 使用 SLAM Toolbox 完成基础建图；
6. 使用 Cartographer 完成第二种 SLAM；
7. 在相同环境和输入条件下比较两种 SLAM；
8. 最终完成导航演示、技术文档和录屏材料。

固定技术环境：

* Ubuntu 24.04；
* ROS 2 Jazzy；
* Gazebo Harmonic；
* Navigation2；
* ros_gz；
* 工作空间为 `~/ros2_ws`；
* 机器人名称为 `diy_nav_bot`。

必须遵守以下规则：

1. 只能使用现代 Gazebo Harmonic，不要使用 Gazebo Classic。
2. 不要使用以下 Gazebo Classic 内容：

   * `gazebo_ros_pkgs`
   * `gazebo_ros`
   * `libgazebo_ros_diff_drive.so`
   * `gazebo.launch.py`
   * `gazebo11`
3. 应使用：

   * `ros_gz`
   * `ros_gz_sim`
   * `ros_gz_bridge`
   * `gz::sim::systems::DiffDrive`
   * Gazebo Harmonic 对应的系统插件。
4. 修改任何文件前先读取现有内容。
5. 不要直接删除现有工程或覆盖用户已有代码。
6. 每次只完成我当前指定的阶段，不要提前完成后续阶段。
7. 所有命令都必须实际执行并检查退出状态。
8. 每次修改后必须运行必要的构建和测试。
9. 出现错误时必须分析根因，不允许通过隐藏错误、注释功能或删除模块来规避。
10. 不要为了消除报错降级到 ROS 2 Humble 或 Gazebo Classic。
11. 安装软件前先使用 `apt-cache policy` 或 `apt-cache search` 检查软件包是否存在。
12. 所有脚本必须具有合理的错误处理，并使用：

    ```bash
    set -euo pipefail
    ```
13. Launch 文件、YAML 和 Xacro 中需要添加必要注释。
14. 所有节点必须统一使用仿真时间：

    ```yaml
    use_sim_time: true
    ```
15. 不允许同时存在多个节点重复发布相同 TF。
16. 项目中 TF 树应遵循：

    ```text
    map
    └── odom
        └── base_footprint
            └── base_link
                ├── left_wheel_link
                ├── right_wheel_link
                ├── caster_link
                ├── laser_link
                └── imu_link
    ```
17. TF 职责必须明确：

    * SLAM Toolbox、Cartographer 或 AMCL 发布 `map -> odom`；
    * Gazebo 差速驱动或里程计系统发布 `odom -> base_footprint`；
    * `robot_state_publisher` 发布 `base_footprint -> base_link` 以及机器人内部 TF。
18. 不允许使用静态 TF 冒充正常的 SLAM、AMCL 或里程计 TF。
19. 所有重要参数必须集中放在 YAML 文件，不要散落在 Launch 文件里。
20. 每阶段结束后停止工作，并按以下格式汇报：

```text
一、本阶段完成内容
二、新建或修改的文件
三、执行过的命令
四、构建结果
五、功能测试结果
六、仍然存在的问题
七、用户需要手动执行的验证命令
八、下一阶段建议
```

不要现在开始创建工程。只需确认你理解了技术环境、工程目标和以上规则。

# 第4段：编写 DIY 机器人 URDF/Xacro

机器人名称：

```text
diy_nav_bot
```

不要复制 TurtleBot3 的完整模型。可以参考 ROS 2 官方写法，但机器人尺寸、结构、颜色和命名应为本项目自行设计。

```text
驱动轮半径：0.075 m

单个驱动轮质量：0.6 kg

前万向轮半径：0.035 m
前万向轮质量：0.15 kg

激光雷达安装高度：约0.23 m
IMU 安装位置：底盘中心附近
```

TF 和 Link 设计：

```text
base_footprint
└── base_link
    ├── left_wheel_link
    ├── right_wheel_link
    ├── front_caster_link
    ├── laser_link
```

Joint 设计：

```text
base_footprint_to_base_link       fixed
```

# 第5段：接入 Gazebo Harmonic

## 提示词5：Gazebo 仿真与传感器

现在执行项目第5阶段：把 DIY 机器人接入 Gazebo Harmonic。

强制要求：

* 使用现代 Gazebo Harmonic；
* 使用 `ros_gz`；
* 不允许使用 Gazebo Classic 插件；
* 不允许使用 `libgazebo_ros_diff_drive.so`；
* 优先从 Xacro 生成 `robot_description`，再通过 `ros_gz_sim` 生成机器人；
* URDF/Xacro 仍然是机器人结构的主要来源。

需要实现以下 Gazebo 系统：

1. 差速驱动；
2. 轮关节状态发布；
3. 2D 激光雷达；
4. IMU；
5. 碰撞和摩擦；
6. 里程计；
7. 仿真时钟。

差速驱动使用现代 Gazebo 系统插件，插件方向应类似：

```xml
<plugin
  filename="gz-sim-diff-drive-system"
  name="gz::sim::systems::DiffDrive">
```

# 通用报错修复提示词

当某个阶段出错时，不要直接进入下一阶段，把下面提示词和完整错误日志一起发给 Codex。

当前项目出现错误。不要重写整个项目，也不要删除已经正常工作的模块。

请按以下步骤排查：

1. 完整读取错误日志；
2. 确认第一个真正的错误，而不是只看最后一行；
3. 检查 ROS 2、Gazebo 和工作空间环境；
4. 确认是否 source 了正确环境；
5. 检查软件包是否来自 Jazzy；
6. 检查是否错误使用 Gazebo Classic API；
7. 检查文件是否被正确安装到 install 空间；
8. 检查 package.xml 依赖；
9. 检查 CMakeLists.txt 或 setup.py；
10. 检查 Launch 参数；
11. 检查 Xacro 展开结果；
12. 检查 YAML 缩进和参数层级；
13. 检查 Topic 名称和消息类型；
14. 检查 TF 是否断裂或重复；
15. 检查 `use_sim_time` 是否统一；
16. 检查 Gazebo Topic 和 ROS Topic 是否正确桥接；
17. 只做最小必要修改；
18. 修改后重新构建和复现；
19. 给出根本原因，而不是只给临时命令。
